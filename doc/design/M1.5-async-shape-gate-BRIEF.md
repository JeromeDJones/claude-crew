# M1.5 — Async, resurfaceable, dual-channel shape-gate (implementation brief)

Status: **ready for `/repo-reactor:repo-react` (a fresh session implements).** Date: 2026-06-12. Authors: Jerome (product) + Kael.

> **Read first:** the *why* is in [`shape-gate-async-surface.md`](./shape-gate-async-surface.md). This brief is the *how* — scope, contracts, touch-points, acceptance tests. Sits between M0 (shipped) and M2 (edge routing): **M0 done → M1.5 (this) → M2 → M1 (deferred).**

---

## 1. One-paragraph summary

M0 shipped a shape-gate where `propose_shape` **blocks the lead's turn** until a human approves via the **dashboard only**, and the gate UI is an **ephemeral modal** that vanishes on navigation. M1.5 keeps the gate invariant (no crew spawns without explicit human approval) but **decouples approval from blocking** and **adds a chat channel**: `propose_shape` returns immediately after surfacing the shape; the operator approves **either** on the dashboard **or** by telling the coordinator in chat; the lead is **notified on resolution via its inbox** (no polling, no freezing); and the gate is **resurfaceable like a surfaced artifact** (notification + tray/badge + re-open, survives navigation). The modal shipped in `shape-gate-modal` is reused as the *visual*; what changes is *when it blocks*, *how it's approved*, and *how it's recalled*.

## 2. Why (the friction, observed live 2026-06-12)

1. **Blocking freezes the coordinator** — a pending proposal halts the lead; it can't chat or supervise. Defeats the supervising-coordinator premise and worsens the "lead burns ctx on relay" friction.
2. **UI-only approval** — no way to approve from a phone / over text / away from the dashboard. The operator should be able to *hear the shape over text and approve by telling the coordinator*.
3. **Ephemeral surface** — the modal disappears on navigation (switch instance → gone). A gate you can accidentally dismiss is fragile; it must be recallable.

## 3. What to build

### 3a. `propose_shape` → non-blocking (server.py)
- Today: parses, `register_proposal`, then **blocks on `await_proposal(timeout)`** and returns the resolved status. (`claude_crew/server.py` `propose_shape` closure.)
- Change: parse, `register_proposal`, **surface** the proposal (3c), and **return immediately** with `{ok: True, shape_id, status: "pending", shape}`. Do **not** block.
- Keep `broker.await_proposal` available for an explicit opt-in blocking caller (`propose_shape(..., wait=True)` may remain as a non-default flag), but the **default is non-blocking**.

### 3b. Chat-channel approval — new lead tool `resolve_shape` (server.py + broker.py)
- New MCP tool **`resolve_shape(shape_id: str, decision: str)`** on the 14-tool lead surface (→ 15) that calls `broker.resolve_proposal(shape_id, decision)` (`"approve"`/`"decline"`). This is how the operator approves **via chat**: they tell the coordinator "approve the shape," the coordinator calls `resolve_shape`.
- Optional companion read **`list_pending_shapes()`** → pending proposals (shape_id, name, crew_id, mermaid/summary) so the coordinator can answer "what's waiting for me?" and *describe the shape over text* before the operator approves. (Recommended — it's what makes phone/text approval ergonomic.)
- `broker.resolve_proposal` already exists with the `pending`-only guard (from the M0 hardening). Reuse as-is.

### 3c. Surface + notify-on-resolve (broker.py + ui_server.py) — reuse the artifact-surface pattern
- **Surface:** model the pending gate on the **artifact-surface system** rather than a transient modal. The artifact machinery to mirror:
  - Tool: `server.py::surface_document` (line ~649) → broker artifact registry.
  - State: `ui_server.py::_build_local_instance` emits `artifacts` (line ~435) **and** `shape_proposals` (line ~445), each carrying `crew_id`.
  - UI: `dashboard.html` `ArtifactTray` (~1207), `ArtifactDrawer` (~1267), unread dots, `MCTopBar` artifact pill + `unreadCount` (~1382). The shape-gate should get the same treatment: a **pending-gate badge/tray entry with an unread notification**, re-openable, **persisting across navigation** (the bug today: the modal is view-tied and vanishes on instance-switch).
- **Notify-on-resolve (no polling, no blocking):** when a proposal resolves (either channel), the broker drops a **message into the lead's inbox** so the lead learns without blocking. Reuse the lead-message channel: `broker._lead_message_condition` + `wait_for_lead_message` + `get_messages` (broker.py ~206, ~860, ~871). Emit e.g. `{type: "shape_resolved", shape_id, status}` to the lead inbox on resolve. The lead's normal `get_messages` loop picks it up, then it calls `instantiate_shape`.

### 3d. Dashboard: resurfaceable gate (dashboard.html)
- Keep the **modal as the visual** (the `shape-gate-modal` slice: `OverlayPanel mode="modal"`, cross-instance `flatMap`, crew_id labels — already shipped).
- Make it **recallable, not transient**: a pending gate shows a **badge/tray entry** (mirror the artifact unread pill in `MCTopBar`); the modal opens from there; switching instances does **not** lose it; closing it leaves the badge so it can be reopened. A pending gate clears from the tray only when resolved (approve/decline) through either channel.
- Approve/Decline in the modal still POST `/shape-approval/{crew_id}/{shape_id}` (UI channel, leader→follower proxy — `ui_server.py` ~823/884, unchanged).

## 4. Invariants (must hold)
- **The shape is still the gate:** `instantiate_shape` still refuses any non-`approved` proposal (zero spawns without human approval). Unchanged.
- **Observable by construction:** resolution flows through the broker; the notify message is on the broker channel.
- **Coordinator-in-the-loop, strengthened:** the lead stays free to supervise/chat; it is notified, not blocked.

## 5. Touch-points (grounded in current master)
- `claude_crew/server.py` — `propose_shape` (make non-blocking); new `resolve_shape` (+ optional `list_pending_shapes`); tool count 14→15(+).
- `claude_crew/broker.py` — emit a lead-inbox message on `resolve_proposal` (+ on timeout/decline); proposal registry already present. `_lead_message_condition`/`send`/`wait_for_lead_message` are the channel.
- `claude_crew/ui_server.py` — `shape_proposals` already in `_build_local_instance`; ensure pending gates carry what the tray needs (title/summary + unread); `/shape-approval` route + proxy unchanged.
- `claude_crew/ui/dashboard.html` — promote the shape-gate to the artifact-style tray/badge + recallable modal (reuse `ArtifactTray`/`MCTopBar` unread patterns); the modal component already exists.

## 6. Acceptance tests (two layers, happy + sad)
1. **Non-blocking propose:** `propose_shape` returns `{status:"pending", shape_id}` **without** waiting; assert the call returns promptly while the proposal is still pending in the broker.
2. **Chat approval:** `resolve_shape(shape_id, "approve")` → `get_proposal(shape_id).status == "approved"`; a subsequent `instantiate_shape` spawns the crew. `resolve_shape(..., "decline")` → declined, instantiate refuses. Sad: `resolve_shape` on unknown id / already-resolved → error (reuse the hardening guard).
3. **Notify-on-resolve:** after a resolve (either channel), a `shape_resolved` message appears in the lead's `get_messages` stream for that `shape_id` + status. Sad: no message before resolution.
4. **UI channel still works:** `POST /shape-approval/{crew_id}/{shape_id}` resolves and (single + multi-instance proxy) — carry over M0's AT11/AT12.
5. **Resurfaceable (Playwright):** a pending gate shows an unread badge/tray entry; opening shows the modal DAG; **switching instances does not lose the pending gate** (the bug fix); resolving clears it. Cross-instance: a follower's pending gate surfaces on the leader (carry over the modal slice's cross-instance test).
6. **`list_pending_shapes`** (if built): returns pending proposals with enough to describe over text; empty when none.

## 9. Open questions (decide during planning)
- Timeout semantics in the non-blocking model: does a pending gate expire, or live until explicitly resolved? (Lean: no auto-timeout by default — it's resurfaceable; an operator can decline. Keep `await_proposal`'s timeout only for the opt-in blocking path.)
- Should `resolve_shape` be the *only* chat path, or also allow the coordinator to surface a one-line shape description automatically when it proposes (so the operator immediately sees it in chat)? (Lean: coordinator describes the shape in its own message when it calls `propose_shape`.)
- Notification payload shape for the lead inbox on resolve (keep minimal: shape_id + status).
