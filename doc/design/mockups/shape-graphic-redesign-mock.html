Design notes — shape graphic redesign

Problem (Jerome's words)

The shape graphic is too cramped. Two surfaces render shapes today and they don't share a visual language: the live TopologyGraph in the rail (dashboard.html ~1612–2024) and the ShapeProposalCard inside ShapeGatePanel (~2631–2774).

The four key moves

  • Room to breathe in the rail — host grows 220→340px based on crew size (was static 240). Header adds a subtitle line and a 3-button control row (− / 1:1 / +) plus an expand button.
  • Expand-to-modal = the real fix. Both surfaces share ONE zoom/pan modal (.modal-backdrop). Wheel = zoom, drag = pan, +/−/1:1 buttons, esc-to-close. Solves "see-the-whole-shape" for any crew size.
  • One node language. The proposal DAG now uses the exact same .nodecard foreignObject HTML labels as the live topology, with a .nodecard.proposed variant (dashed accent border) for the "not yet instantiated" state. Edge colors come from --edge-* tokens in both. Reading the proposal then feels like reading a future state of the topology, not a different idiom.
  • Light-touch responsive at 1024px. Two-pane stays. The 320px rail becomes clamp(220px, 22vw, 260px); .nodecard min-width drops to 72; roster padding shrinks. NO drawer collapse, NO single-column. The zoom modal works at every width and is the universal escape hatch for narrow rails.

Edge color reuse

Identical across both surfaces (live + proposal):

  • --edge-direct #22c55e
  • --edge-tee #3b82f6
  • --edge-gated #f59e0b
  • --edge-tripped #ef4444

Mechanical deltas to dashboard.html

1. MissionControlLayout (~2906) — replace inline grid:

// before
<div style={{ display: "grid",
  gridTemplateColumns: "320px minmax(0, 1fr)", minHeight: 0 }}>
// after
<div className="dash-grid">
// (with .dash-grid + @media (max-width: 1024px) rules in CSS)

2. TopologyGraph (~1612–2024) — three additive changes:

  • Add a topo-head row above .topology-host with title + subtitle + zoom controls + expand button (replaces the current section title rendered above the host).
  • Wrap the mermaid SVG mount in a .pan-layer div and bind wheel/mousedown/mousemove handlers on .topology-host that update a {zoom,tx,ty} state, applied via transform: translate() scale(). The existing edge-decoration code in the useEffect at ~1779 is untouched — it operates on the same SVG regardless of transform.
  • Bump host sizing: minHeight: 220, maxHeight: 340, height: clamp(220, 240 + 18 × max(0, agents.length − 3), 340). The 320px-rail no longer constrains shape comprehension — the modal does.

3. New TopologyExpandModal component — mounted at MissionControlLayout root, opens on the expand button click; renders a fresh mermaid run with the same mermaidSrc; reuses window.mapEdgeStatsToPaths for decoration; shares state with the rail's selectedEdge via lifted state OR opens its own panel (recommend the former — clicking an edge in either view selects it everywhere).

4. ShapeProposalCard (~2631–2726) — two changes:

  • Replace the row layout (flexDirection:'row', diagram maxWidth: 420, controls right) with the same modal-driven full-screen view. The card in the gate-panel list becomes a preview tile (small DAG thumbnail + crew + shape_id + Approve/Decline). Clicking the thumbnail opens the zoom modal.
  • Generate the proposal's mermaid source through a new shared helper shapeToMermaidUnified(shape, { proposed: true }) that emits .nodecard.proposed labels and uses the same --edge-* colors per declared edge mode. Drop the raw proposal.mermaid string passthrough for live-rendered consistency. (If the server-side shape_to_mermaid in shapes.py needs to gain the variant flag instead, do it there — the dashboard payload stays as the source of truth.)

5. ShapeGatePanel (~2730–2774) — keep it as the list shell, but each card opens the unified modal on click instead of rendering a side-by-side diagram in-place.

Open design questions for you

  1. When the topology is expanded in the modal AND a new shape proposal arrives, do we (a) auto-switch the modal to the proposal, (b) stack a toast, or (c) badge the topology modal? I went with (b) implicit + the gate-pill in the topbar already exists.
  2. Should the in-rail topology auto-fit (recompute zoom/pan to fit on every shape change), or stick to a stable default and let the user re-fit? Mockup shows: auto-fit on shape change, manual after first interaction.
  3. Below 1024px, do we want the rail topology to still render in-rail (with the expand affordance) or to collapse to a topbar pill that opens the modal directly? Mockup keeps it in-rail because losing the at-a-glance shape preview hurts more than the squeeze. Reasonable to disagree.
  4. Selected-edge panel placement at narrow widths — currently sits below the host in the rail. Should it always migrate to the modal foot at <1024px? Mockup keeps it in-place; modal foot is reserved for when the edge is clicked from inside the modal.

What I did NOT touch

  • Edge keyed lookup (window.mapEdgeStatsToPaths) — load-bearing for BC-03 reciprocal-pair correctness; reused unchanged in the modal.
  • Gated-bridge expansion logic (displayEdges useMemo) — preserved verbatim; modal sees the same display edges.
  • Edge-click → /edge-log/<crewId> fetch — preserved; matters for multi-instance proxy (see CLAUDE.md trap).
  • Roster + status dot colors — every --st-* token reused as-is.
