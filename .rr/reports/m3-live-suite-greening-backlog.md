## BL-1: F7 telemetry regression — TNM tool_use_id no longer correlates with PostSubagentUse hook tool_use_id (SDK 0.1.68)

**Classification:** SDK behavior drift / telemetry degradation  
**Severity:** Low (functional, benign noise)  
**Confirmed via:** Runtime debug probe during live test run (2026-06-17)

### What was observed

`_end_turn: no TNM for subagent tool_use_id=... defaulting outcome from hook` warnings fire
on every subagent dispatch in SDK 0.1.68. The F7 correlation loop in `_end_turn`
(sdk_teammate.py) looks up `_task_notifs_by_tool_use_id[closed.tool_use_id]`, where
`closed.tool_use_id` comes from the PostSubagentUse hook. But the
`TaskNotificationMessage.tool_use_id` arriving via `_collect_response_text` is a
**different identifier** for the same dispatch — the IDs don't match.

Debug trace (one turn, real IDs from test run):
```
DEBUG-TNM:    tool_use_id='toolu_01ARWn4ZhNzwzBpVSKcmqrU1' status='completed'
DEBUG-SCRATCH: closed.tool_use_id='toolu_01BxnupTb35dYZZ4rBDf3xXo' hook_outcome='ok'
               task_notifs_keys=['toolu_01ARWn4ZhNzwzBpVSKcmqrU1']
```

The TNM `tool_use_id` is not None — it just refers to a different object than
what the PostSubagentUse hook surfaces. This appears to be a behavioral change
in how the SDK routes task notification IDs relative to tool-use IDs starting
in some release ≤ 0.1.68.

### Impact

- All subagents SUCCEED (hook_outcome='ok' in every case observed).
- The fallback outcome derivation from `hook_outcome` is correct.
- The `tnm_missing=True` JSONL field is written, which is accurate.
- **No production failure.** Telemetry is degraded: `subagent_result` records
  have `summary=None` and `tnm_missing=True` instead of the TNM summary.

### What needs investigation

1. Determine the correct SDK 0.1.68 mapping: what field on `TaskNotificationMessage`
   corresponds to the PostSubagentUse hook's `tool_use_id`? (Candidates: `task_id`,
   a new field, or the TNM's `tool_use_id` now being the parent task's tool_use_id
   rather than the child subagent's.)
2. Once the correlation key is identified, update `_collect_response_text`'s
   `record_task_notif` call site (sdk_teammate.py:364) and `_end_turn`'s lookup
   to use the correct key.
3. Add a regression test that asserts `tnm_missing=False` in the JSONL for a
   successful subagent dispatch.

### Files to change

- `claude_crew/sdk_teammate.py` — `_collect_response_text` (line ~364) and
  `_end_turn` (line ~1111)

## BL-2: permission_mode='plan' no longer blocks Write in headless SDK sessions (CLI 2.1.177)

**Classification:** Production permission-gate regression  
**Severity:** HIGH — affects all teammates declared `permission_mode: plan`  
**Confirmed via:** Live test `test_plan_mode_blocks_file_write_and_cwd_works` (probe.txt exists)

### What was observed

A teammate spawned with `permission_mode="plan"` (correctly wired to `--permission-mode plan`
in the CLI subprocess) executed a `Write` tool call without blocking. The plan teammate
created `probe.txt` when it should have been blocked.

Wiring is confirmed correct:
- `sdk_teammate.py:1448-1452`: `opts_kwargs["permission_mode"] = "plan"` is set
- `transport/subprocess_cli.py`: `--permission-mode plan` is appended to the CLI command
- `ClaudeAgentOptions.permission_mode: PermissionMode | None` field exists in SDK 0.1.68
- `claude --help` shows `--permission-mode plan` as a valid choice

### Hypothesis

In CLI 2.1.177, plan mode presents a **plan-approval UI** rather than silently blocking
tool execution. In headless/non-interactive SDK subprocess sessions there is no UI to
pause execution, so tool calls proceed anyway. The behavioral contract changed:
plan mode was previously "block writes until approved"; it is now "show plan UI" which
is a no-op in headless mode.

### Impact

- Production coordinators that spawn teammates with `permission_mode: plan` (e.g., to
  gate tool execution on human approval) are NOT getting the gate. Tools execute freely.
- This is a **security/safety regression** for any workflow that relies on plan mode
  to require human sign-off before file writes or other mutations.

### What needs investigation

1. Confirm the CLI 2.1.177 release notes for permission_mode='plan' behavioral changes.
2. Determine if there is an alternative mechanism for headless plan-mode gating
   (e.g., `can_use_tool` callback in `ClaudeAgentOptions`).
3. If there is no equivalent, document the limitation in `CLAUDE.md` under
   "Known limitations" and update any feature spec that relies on plan-mode blocking.

### Files to change

- `doc/ARCHITECTURE.md` or `CLAUDE.md` — document known limitation
- Potentially `claude_crew/sdk_teammate.py` — implement `can_use_tool` callback as
  an alternative permission gate if the CLI plan-mode gate is gone
- `tests/test_live_sdk.py:test_plan_mode_blocks_file_write_and_cwd_works` — currently
  marked `xfail(strict=False)`; update to `xfail(strict=True)` once a replacement
  gate is implemented, then un-xfail when the new gate proves it blocks correctly.

## BL-3: atlassian MCP server registered but not credentialed for SDK subprocess sessions

**Classification:** Environmental / known limitation  
**Severity:** Low (test gate handles it; no production impact if atlassian MCP is not used)

### What was observed

`test_pack_string_name_produces_reachable_server` skips when the atlassian MCP
server (`https://mcp.atlassian.com`, type=http) is registered in `~/.claude.json`
but the teammate reports no `mcp__atlassian__` tools. The server requires Atlassian
OAuth credentials that are not available in SDK subprocess sessions in this environment.

### Impact

- The MCP wiring (pack `mcpServers: ["atlassian"]` → `ClaudeAgentOptions.mcp_servers`)
  is verified by pack-assembly assertions before the live call.
- The live tool-availability assertion skips rather than hard-fails.
- No production impact unless a pack declares `mcpServers: ["atlassian"]` expecting it
  to work — in that case operators must ensure the server has working credentials.

### What needs investigation

1. Determine how atlassian MCP OAuth auth works for SDK subprocess sessions vs.
   interactive Claude Code sessions (the interactive session presumably has a token
   from `claude auth login`; the subprocess may not inherit it).
2. If there's a way to thread auth tokens into the subprocess env, document it
   in `doc/sdk-teammate-wiring.md`.

## BL-4: ~~delegation prompt not reliable for Bash-natural tasks~~ — CLOSED

**Status: RESOLVED** in the m3-adaptation-algebra improvement pass.

**Root cause identified:** The `general` role is a leaf-node subagent pack definition
that explicitly restricts tools to `[Read, Grep, Glob, Edit, Write, Bash, WebFetch,
WebSearch]`. No `Task` tool → the model could not dispatch subagents even when asked.
The original test was ill-posed: it asked the model to "use the explorer subagent" but
didn't give it the Task tool needed to do so.

**Resolution:**
1. Re-targeted the test to use an explicit Task-tool directive (not a judgment call).
2. Spawn now includes `extra_tools=["Task"]` — mirroring how a real coordinator grants
   delegation capability to a teammate.
3. Test passes reliably across 3/3 live runs (10-15s each).
4. xfail decorator removed; test is now a real passing mechanism test.

See `tests/test_live_teammate_delegation.py` for the updated test.
