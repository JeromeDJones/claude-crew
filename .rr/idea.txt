teammate-death-diagnostics — capture durable diagnostics when an SDK teammate dies

>> Goal / user-visible outcome

When an SDK teammate dies (the node `claude` CLI subprocess exits non-zero and the
SDK raises ProcessError), the next OCCURRENCE must be self-explaining. Today a death
produces an opaque envelope to the lead ("...crashed: Command failed with exit code 1")
and we have NO record of WHY: the subprocess stderr is discarded, the death site logs
nothing, and we never capture what the teammate was doing. Operators (and the
coordinator) should be able to read, after the fact, exactly why a teammate died.

This is DIAGNOSTIC TELEMETRY, not a behavioral fix. We are deliberately NOT trying to
prevent the death or change control flow — we are making the next organic death
diagnosable. It closes two backlog items: the 2026-06-04 "SDK teammate dies on a
non-zero Bash exit" entry (its stated root cause is a MISDIAGNOSIS — see below) and the
2026-05-24 "subprocess death undiagnosable because we discard stderr" entry.

>> Three deliverables (priority order)

1. PER-TEAMMATE STDERR RING BUFFER (the load-bearing piece). Register a `stderr`
   callback on the SDK client options so the node CLI's stderr is captured into a
   bounded ring buffer (last ~50 lines, also byte-capped) on the SdkTeammate. On death,
   the redacted tail is attached to the death record. This is the ONLY way to see why
   the CLI exits.

2. LAST-TOOL-BEFORE-DEATH CONTEXT. Snapshot what the teammate was doing when it died —
   especially the last Bash command + its outcome, plus any in-flight tool — into the
   death record. This directly tests the backlog's assumed "non-zero Bash exit"
   correlation: next death, we will SEE whether a Bash exit-1 was actually in flight.

3. LOG + ATTACH AT THE DEATH SITE. At the ProcessError/CLIConnectionError/BrokenPipe
   match site, emit a WARNING with exc class name, exit_code, the stderr tail, and the
   last-tool context — and attach the same to the broker death record so it surfaces on
   the dashboard and in the transcript.

>> SDK-flow context — REQUIRED reading for whoever writes the spec

The implementor will NOT know how claude-agent-sdk drives teammates. The spec must
carry this so the implementor needs zero SDK-internals discovery.

- claude-crew's SdkTeammate (`claude_crew/sdk_teammate.py`) drives a node `claude` CLI
  subprocess via the SDK's ClaudeSDKClient. Options are built around line 1376
  (`options = ClaudeAgentOptions(**opts_kwargs)`) then `async with
  ClaudeSDKClient(options=options) as client:` (~1378).

- The SDK's SubprocessCLITransport spawns the node process and pipes stderr ONLY when a
  callback is registered:
    subprocess_cli.py:447  →  stderr_dest = PIPE if self._options.stderr is not None else None
    subprocess_cli.py:493-506  →  _handle_stderr() reads lines and calls self._options.stderr(line_str)
  claude-crew currently passes NO `stderr` callback, so the CLI's stderr is inherited
  into the server's own stream — unattributed and effectively lost. ClaudeAgentOptions
  has a `stderr` field that takes a callback `Callable[[str], None]` invoked per line.
  THIS is the supported hook to add.

- When the node CLI exits non-zero, the transport raises
    ProcessError("Command failed with exit code N", exit_code=N)   (subprocess_cli.py:673-676)
  surfacing during the receive_response() drain. ProcessError carries `.exit_code` and
  `.stderr` fields (_errors.py:25-40), BUT the transport raises it with stderr=None — so
  the exception itself does NOT carry the why. We must capture stderr ourselves via the
  callback above.

- claude-crew catches it at the generic except arm in `_handle_one_turn`
  (sdk_teammate.py:1479-1491): matches ProcessError/CLIConnectionError/BrokenPipe by
  class name, sets _death_suspected=True, stores the in-flight envelope, returns
  SILENTLY — no log of the exception, exit_code, or context. The liveness poll
  (sdk_teammate.py:1168-1207) then calls broker._handle_teammate_death(exit_code=...).

- The death record / tombstone is built in `broker.py` `_tombstone_teammate`
  (~366-560); TeammateInfo death-record fields are ~46-88. New diagnostic fields attach
  here and flow to the dashboard/transcript.

>> Expected vs actual

ACTUAL: a ProcessError death → opaque "crashed: Command failed with exit code 1"
envelope, teammate tombstoned, zero record of why (stderr discarded, death site silent,
no tool context).

EXPECTED: on death we capture + persist (a) last ~50 lines of CLI stderr (redacted),
(b) last tool invoked (esp. last Bash command + outcome) + any in-flight tool at death,
(c) a WARNING at the death site with exc class + exit_code + stderr tail + last-tool.
All attached to the death record; visible on the dashboard and in the transcript.

>> Constraints / non-negotiables

- SECRETS: stderr can contain tokens/env. It MUST go through `claude_crew/redaction.py`
  (`redact_error` / `redact_output`, honor REDACTION_VERSION) before ANY persistence
  (death record, transcript, dashboard).
- BOUNDED: ring buffer uses a deque(maxlen=...) plus a byte cap — never unbounded.
- ADDITIVE ONLY: do not change death/tombstone control flow or existing error-envelope
  semantics. Telemetry only.
- The stderr callback must be cheap, non-blocking, and never raise out of itself (a
  raising callback could destabilize the SDK's stderr reader task). Just append.
- Reuse existing tracking: `_tool_uses` (in-flight dict), `_last_tool_completed`, and the
  PreToolUse/PostToolUse hooks (F8) already in sdk_teammate — do not build a parallel
  tool tracker.

>> Verification (two layers, happy + sad — per repo standards)

- Implementation layer (stub/unit): ring buffer is bounded + redacted; death-record
  attachment populated by injecting a ProcessError and feeding synthetic stderr lines.
  Sad: secret-bearing stderr → assert redacted; empty stderr → graceful empty/None, no
  crash.
- Integration layer: a GATED live SDK test (CLAUDE_CREW_LIVE_TESTS=1) that spawns a real
  teammate, runs an ordinary turn, and asserts the stderr callback received normal CLI
  stderr lines — proves the wiring end to end WITHOUT needing to force a crash. Plus a
  stub-mode broker test asserting death-record fields populate on tombstone.
- Honor CLAUDE.md test conventions: bounded async-iterator drains; HOME-monkeypatch SDK
  auth preservation for live tests; run the FULL `uv run pytest` at the validation gate
  (this touches widely-consumed teammate/broker behavior).

>> Explicitly OUT OF SCOPE (do not chase)

- Do NOT fix or prevent the node CLI exiting non-zero — the distal cause is unknown;
  this telemetry is how we will learn it.
- Do NOT add session-resume / retry-on-ProcessError resilience — separate future call.
- Do NOT implement the backlog's "catch the non-zero-exit tool error and feed it back as
  the tool result" — that is a MISDIAGNOSIS. claude-crew never sees individual tool
  results; by the time we catch ProcessError the subprocess is already dead. There is no
  live model to feed.
- No dashboard redesign — surfacing the new fields in the existing death/status
  rendering is sufficient.
